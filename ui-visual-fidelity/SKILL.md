# UI Visual Fidelity

## 核心原则

已被用户接受的界面就是视觉契约。先确定基准，再修正最小的根因，最后同时证明交互正确和视觉一致。自动测试通过不等于设计已经还原。

## 工作流程

1. **锁定范围与基准**
   - 把本轮要求拆成可观察的结果，并记录明确禁止改动的区域。
   - 用户说“只改这一点”时，不顺手清理、统一或重设计其他模块。
   - 若项目存在 `AGENTS.md`，读取其中的结构基准与视觉基准；“上一版”必须落实到提交、文件或截图，不能凭记忆推断。

2. **先取证，再编辑**
   - 在指定页面、主题、状态和视口复现问题。
   - 检查目标元素、父层级、计算后样式、层叠顺序、伪元素、裁切和层级关系。
   - 对齐问题以最终像素观感为准；CSS 显示 `center` 不能替代视觉核验。

3. **修改最小归属层**
   - 优先修正拥有该样式的组件、令牌或选择器，不用全局后置覆盖掩盖局部问题。
   - 复用现有精确颜色、圆角、边缘和悬停模板，不发明“差不多”的样式。
   - 黑夜与白天模式分别拥有颜色和背景；共享结构与交互，除非设计明确要求不同。
   - 用户要求直接处理图片时，输出处理后的素材文件；不要把旋转、翻转等补偿留在 CSS 中。

4. **视觉验收是独立门槛**
   - 先写能捕获回归的自动检查，再修改代码。
   - 在真实浏览器核验相关页面、展开/收起/悬停/弹窗状态，以及黑夜和白天模式。
   - 对照基准截图和计算后样式。颜色、形状、位置或层级仍有差异时，必须记录为未完成，不能因测试通过而宣称还原。

5. **稳定后再整理代码**
   - 把重复颜色、渐变、阴影、圆角抽成语义变量。
   - 给彩虹边框、玻璃面板、普通按钮建立真正可复用的组件或 CSS 模板。
   - 按胶囊、项目、抽屉、Feedback、AI、白天模式等视觉职责拆分模块。
   - 逐步把后置覆盖移回所属组件，并减少 `!important`。
   - 合并规则前确认选择器优先级、导入顺序和状态覆盖保持不变。
   - 精简行数不是目标；不改变页面位置、效果和交互才是目标。

6. **交付与版本控制**
   - 增加格式/架构检查和页面截图对比测试；测试用于防回归，不替代人工视觉验收。
   - 报告修改范围、验证结果和仍存在的视觉差异。
   - 大范围整理前保留安全提交。只有用户明确下达上传口令时才提交并推送。

## 质量边界

“稳定、模块归类良好、重复控制良好、可维护性中上”不等于“世界顶尖工程师眼中的终态代码”。如果仍有大量硬编码颜色、过长选择器、后置覆盖或较高的 `!important` 比例，应如实标记为架构优化空间；不能只因为行数减少或检查通过就宣称已经漂亮、完整还原。

## 快速判断

| 情况 | 应对方式 |
|---|---|
| 测试通过但截图不同 | 继续修正，视觉门槛未通过 |
| 当前代码更整洁但颜色偏移 | 保留基准颜色，撤销造成偏移的抽象 |
| 单元素异常 | 检查元素及父层，不增加全局覆盖 |
| 新页面需要同款组件 | 复用基准模块与令牌，并做深浅双模式对照 |
| 用户指定旧版本 | 只提取目标视觉属性，不整版回退 |

## 红旗

- “看起来差不多”
- “测试都绿了，所以完成了”
- “最新提交自然就是视觉基准”
- 为修一个元素加入覆盖整站的选择器
- 借重构改变颜色、圆角、间距或层级
- 用户只要求一个点，却同时修改其他模块

出现任一红旗，停止扩散修改，回到范围、基准和真实页面取证。
